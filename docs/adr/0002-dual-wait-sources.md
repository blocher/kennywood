# Dual Wait sources (ThemeParks.wiki + Queue-Times)

Kennywood Waits always loads live Wait times from both **Queue-Times** park 312 and **ThemeParks.wiki**. Both go through the same-origin `/api/waits?source=` Pages Function (Vite mirrors it in dev). There is no preferred-source setting: every Attraction row presents the values as equal peers with the user-facing labels **Posted in Park** (Queue-Times) and **Listed in App** (ThemeParks.wiki / Herschend Pulse).

Queue-Times is the base for the catalog join and Wait range filtering because in-person observations have found that it usually matches Kennywood's physical signs. Users can sort by either value; **Posted in Park** is the default sort, with the other Wait as the secondary key (so missing Park values order by App, and vice versa). The Queue-Times/sign relationship is observed, not a confirmed upstream contract: Queue-Times does not publish the Kennywood system it collects from. ThemeParks.wiki supplies broader Attraction coverage, and its Kennywood adapter reads Herschend Pulse destination 701, matching the current official app. Attractions missing from Queue-Times remain listed with Posted in Park `—` when the ThemeParks.wiki feed or the Attraction catalog knows about them.

The footer gives a short description of both values, with API details, normalized fields, and provenance uncertainty inside a native **Read more** disclosure. Queue-Times' required prominent attribution remains present as **Powered by Queue-Times.com**.

Client poll and edge Cache API TTL are **~5 minutes**, matching ThemeParks.wiki’s live-data guidance. Optional `THEMEPARKS_API_KEY` (Pages secret / `.env` / `.dev.vars`) is sent as `x-api-key` so rate limits count against this app’s key. Successful `/api/waits` bodies are stored in `caches.default` so browsers share upstream fetches rather than each visitor triggering ThemeParks.
